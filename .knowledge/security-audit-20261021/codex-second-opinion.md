設計の評価です。ファイルは変更していません。以下、auth＝`.designs/20261021-auth-hardening.md`、http＝`.designs/20261021-http-hardening.md`。

**1. master のログインパスワード再入力**

- **盗まれたセッションだけで無効化させない目的には妥当**です。公開定数より明確に改善し、監査 `A-auth.md` の AUTH-01 自体も再認証を代案にしています。ただし独立した第二要素ではありません。
- N-1 の「同じ防御」は限定的です。**ログインパスワードまで漏れた場合、独立して保管されたランダム秘密なら残る防壁が失われます**。弱いログインパスワードなら推測耐性も下がります。master 初期パスワードを形式検証から除外する M-3 は、この点で気になります。
- **再認証自身のロック拒否が曖昧**です。M-7／H-3 は失敗加算と「以降 login が429」を規定していますが、`reauth`／`update/password` 自身が、照合前に同じロックを検査する保証がありません。加算だけなら盗難 token から推測を続けられます。両経路での事前拒否・入力長制限が条件です。
- パスワード再入力には nonce・操作対象への結び付けがなく、**捕捉された token＋password は再利用可能**です。固定ランダム秘密も同様で、これは置換固有の劣化ではありません。ただし別ホスト間の平文 HTTP を private network だけで守る §10.4 は不十分。TLS 等の通信保護が必要です。操作単位のリプレイ防止まで要求するなら、対象・操作に結び付いた短命・一回限りの認可が別途必要です。

参照：auth §11 N-1（701行）、§5 M-3/M-7、H-3、§10.4。**条件付き一致**

**2. レート制限と PBKDF2 予算**

残る具体的な攻撃は次です。

- **ロックアウト DoS**：被害者 ID に5回失敗すれば、正しいパスワードでも15分拒否。解除後に繰り返せます。同一 NAT の30失敗は他の利用者も巻き込みます。「成功を数えない」だけでは巻き添えを防げません。
- **成功ログイン連打**：攻撃者自身の有効アカウントなら IP／アカウント失敗制限を通らず、PBKDF2 予算を継続消費し、セッション作成・削除・ログ書込みも誘発できます。IP ローテーション／IPv6 アドレス変更は signup 制限も迂回します。
- **予算外の DB DoS**：signup は予算確認より前にカウンタを書きます（391行）。したがって多 IP から不正 signup を送れば、PBKDF2 予算と無関係に行数・書込みを増やせます。§13 の「予算で毎秒16行以下、最大約58k行」は成立しません。
- **並行試行の超過**：原子的な加算だけでは「ロック確認→ハッシュ→加算」全体は原子的になりません。同時実行で閾値を超える試行が通る余地があります。厳密な上限には試行枠の予約が必要です。

**予算だけで verify 遅延を守れる、という N-7 には反対です。** sync worker はハッシュ実行中に verify を処理できません。容量8のバーストで全 worker が同時に埋まり得ますし、拒否要求も受付・JSON解析・ログ・DB処理を消費します。さらに `4 hash/s × 123.7ms ≈ 50%` はその測定環境の平均値であり、CPU 割当てや競合が変われば成立しません。worker 数に比例して総予算も増えます。

予算は有効な補助策ですが、代案は **入口で成否を問わない要求数・同時実行制限と、verify 用の独立 worker pool／受付経路・CPU余力の確保**です。共有 DB の競合も含め、攻撃負荷下の遅延検証が必要です。

参照：auth §4.1（153–160行）、§5 L-16/L-17、366・391行、§11 N-5/N-7、§13。**不一致**

**3. autoescape／Markup の契約**

既定 ON は HTTP-01 の修正として賛成ですが、**現状の「安全」の範囲は広すぎます**。

- **引用符付きでも危険な属性があります**。`onclick="{{ x }}"` に `alert(1)`、`srcdoc="{{ x }}"` に HTML を渡す例です。後者は属性の文字参照が復号された後、再び HTML として解釈されます。`style` も別の CSS コンテキストです。E-R6 は通常のテキスト属性に限定する必要があります。[OWASP も属性・JS・CSS を区別しています](https://cheatsheetseries.owasp.org/cheatsheets/Cross_Site_Scripting_Prevention_Cheat_Sheet.html)。
- **E-R8 の「壊れるが安全」は誤り**です。`<script>let x={{ x }};</script>` に `alert(1)` を入れると、エスケープ対象文字なしで実行できます。非対応とするのは可能ですが、安全性は保証できません。
- **HTML 断片の安全性は属性へ持ち運べません**。ネストした `render()` の出力には生の引用符があり得るため、属性スロットへ渡すと境界を壊します。`Markup` は HTML 本文への挿入専用という制約が必要です。
- **`safe_url()` が `escape(value)` を使う点にも穴**があります。例えば `Markup("jav&#x61;script:alert(1)")` はスキーム検査を通り、Markup のため再エスケープされず、属性では `javascript:` に復号されます。URL ヘルパは既存の HTML 安全印を信用せず、URL として検証して属性用に符号化すべきです。
- E-R10 の「Markup でも常にエスケープ」と、`escape()` の「Markup は素通し」も矛盾しています。`json_script()` は安全な受渡しには有用ですが、その後の `innerHTML` 代入までは守りません。

「自作40行」という長さは安全性の根拠になりません。上記のコンテキスト制約・ヘルパの整合性を満たすことが採用条件です。§6 の既定 CSP にスクリプト制限はなく、これらの穴を補完しません。

参照：http §4.1（81–85行）、§4.3 E-R3/E-R6/E-R8/E-R10、§6.4、§21-1/3。**条件付き一致**
